## 硬件原型验证

- 遥控器麦克风音频、Codex F5 听写、松开转写、确认键发送。
- 快速点按后再长按的稳定性。
- 真实断开蓝牙后，按键和 ATVV 音频订阅自动恢复；恢复后输入和发送成功。
- 整机重启后的图形会话自启动与实际使用。
- 后续新增的返回键：Codex 中退格、长按删除与松手；浏览器中返回上一页。

返回键改动后未再次执行整机重启。按住返回键时切换焦点、断线释放主要由模拟测试覆盖。

## 客户端播放保护实测

2026-11-12，在上述原型环境及客户端 `26.1103.32239` 上应用与公开包相同的播放保护后，完成一次 **114.67 秒、277 次采样**的只读观察，没有保存录音，查询错误为 0。

- 用户明确确认：开始录音时，QQ 音乐没有变小。这是本次已经确认的听感结果。
- 监测捕捉到 4 次独立的听写辅助程序运行和 4 个 ChatGPT 录音流。记录到的 QQ 音乐、微信、客户端播放流及遥控器 `pw-cat` 音频流，其原生 `volume` 始终为 `1.0`、`mute` 为 `false`，`channelVolumes` 中各声道均为 `1.0`。
- 结束检查时，F5 已释放，客户端播放保护仍有效。观察到播放流增益正常，不等于用户已经逐项听过并确认所有消息提示音或语音内容。

本机原来排障使用的临时 WirePlumber 规则文件已删除，共用 Chromium 输出的低增益记录已清除；此前临时改动的两项恢复设置均已恢复为 `true`。默认显示器 HDMI 输出和 `sayall-mic` 输入保持不变。这些是本机排障收尾，不是公开安装程序会对其他电脑执行的步骤。旧会话可能仍保留规则缓存，因此 **`alpha.2` 在重新登录或整机重启后的验证尚未完成**。

此次使用的是本机原型桥接加相同的播放保护，通用安装程序没有替换本机现用服务。结果只支持本次环境和观察时段内未见听写压低播放增益；长期稳定、所有通知音听感、另一台干净电脑安装及腾讯会议仍待验证。公开包只记录汇总结论，不包含私人诊断原始文件。

## 发布前的音频兼容验证

当前测试环境发现了客户端听写降音量与播放音量保存、恢复相关的风险，详见[故障排查](TROUBLESHOOTING.md#听写后音乐或消息提示音越来越小)。一次恢复声音、单次听写成功或几分钟观察通过，都不能代替长期使用验证。

安装播放保护后，在每个准备声明支持的客户端版本和 Linux 环境中，记录以下结果：

- 播放音乐时连续进行多次听写；逐次对比开始前、录音中和结束后的播放增益与实际音量，要求录音本身不压低或抬高其他声音输出。
- 在听写前后切歌、调低再调高音量、静音再取消静音，确认新建播放流不会继承异常低增益。
- 检查微信等应用的语音播放、新消息提示音及客户端自身完成提示音；不能只测试当前正在播放的音乐。
- 分别验证蓝牙断开重连、音频服务重启、图形会话重新登录和整机重启后的播放与录音。音频服务重启后，应确认客户端重新枚举并连接麦克风；系统存在 SayAll Mic 不能代替客户端实际波形和转写验证。
- 检查其他跟随默认输入的应用：按语音键会切换默认麦克风，松开后会尝试恢复，记录是否发生意外切换或未恢复。
- 验证客户端更新或保护脚本被更改时，遥控器拒绝开始听写、按住状态被释放，并显示可理解的保护失效原因；不得自动套用未知版本适配。
- 停止桥接后，验证恢复客户端原文件与再次保护。操作必须先预览，并确认未覆盖更新后的客户端或用户另行修改的文件。
- 保存每项测试的环境、次数、观察时长和失败条件，不把“暂未复现”标记为“长期稳定”。

自动测试不执行这些实物流程，也不自动写入系统音频兼容规则。默认方案从已知客户端的降音量触发源实施保护；本机短时多次听写已获得上述听感与增益监测结果，但整个清单尚未全部完成，尤其不能省略清理旧规则后的重新登录或重启验证，也不能将短时结果写成长期兼容保证。

## 发布阶段

这是 `0.1.0-alpha.4`，不是跨发行版兼容性承诺。通用安装程序尚未在另一台干净电脑实际安装；其他遥控器、原生 Wayland Codex 窗口、其他桌面环境、腾讯会议和长期连续录音均待验证。

下一次实际部署应依次验证：客户端播放保护 → 安装和权限 → F5 与音频 → 音乐及提示音不受听写影响 → 确认发送 → Codex、微信和浏览器中的返回键 → 蓝牙重连 → 重启 → 卸载及客户端恢复。
