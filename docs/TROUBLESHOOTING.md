# 故障排查

先运行 `/usr/bin/python3 -B scripts/doctor.py`，再查看：

```bash
journalctl --user -u sayall-bridge -u xiaomi-codex-keys -n 80
```

## 没有 SayAll Mic

确认 SayAll 已安装、蓝牙服务正常、所选遥控器已连接，并且 `sayall-bridge.service` 正在运行。停止桥接后虚拟麦克风消失是预期行为。检查 `pw-cat`、`pw-loopback`、`pw-dump`、`wpctl` 是否存在。

## 系统有麦克风，客户端却提示没有连接

先区分系统设备是否存在与客户端是否重新连接。当前测试环境曾在重启音频服务后出现：系统中仍有 `sayall-mic`，蓝牙已连接，桥接日志也有音频帧，但客户端旧的音频服务没有重新连接，因而提示没有麦克风。

先关闭听写入口再重新打开；如果仍未重新识别设备，保存当前工作并正常退出、重新启动客户端，然后测试波形和转写。不要照抄旧进程编号结束进程，也不要因客户端未刷新就反复修改遥控器映射或系统默认设备。这个问题只在当前测试环境得到验证，不能推断所有客户端或 Linux 版本都采用相同行为。

## 听写后音乐或消息提示音越来越小

当前测试客户端带有名为 `dictation-ducking` 的听写降音量组件。检查其本地代码发现，它会扫描 `Stream/Output/Audio` 播放流，将当前原生 `volume` 乘以 `0.25`；结束时，只对仍存活、对象序列号相同且当前增益接近预期压低值的流恢复原值。这是当前所用客户端的行为，代码不在遥控器项目中，也未确认它是否属于所有官方客户端版本的通用实现。

本机曾测到播放增益为 `0.0625` 和 `0.000244`，而 PulseAudio 声道音量仍显示 100%；WirePlumber 又按 `application.name=Chromium` 共用保存播放音量。临时降音量与共享记忆可能使衰减被保存、继承，或在恢复失败后继续累积。自动压音量机制已经确认，但每次触发与恢复失败的完整因果链尚未逐次捕获，不能把推测写成所有用户必然遇到的问题。

排查时应对比听写前、听写中、松开后以及新建播放流时的原生总增益；同时检查应用是否主动静音或调低音量。不能仅凭界面的百分比判断正常，也不能仅按共用的 `Chromium` 名称修改所有应用。节点编号会变化，其他机器的编号和固定修复命令不可直接套用。

`alpha.2` 将[客户端播放保护](../README.md#2-先启用客户端播放保护)作为必要安装步骤，停用已核实客户端的降音量辅助程序；安装及运行时均检查保护状态。替代程序只等待生命周期结束，不访问音频设备或调用音频命令。未知客户端文件会拒绝修改，保护失效会暂停遥控器听写。

默认安装仍不修改 PipeWire / WirePlumber 配置，也不会自动修复其他应用已经遗留的低增益。本机曾额外使用的音量记忆规则不随项目分发：停用共用音量记忆只能针对传播路径，不能阻止客户端主动压低播放音量，因此不是此完整方案的替代步骤。

本机保护部署后的短时实测中，用户确认录音开始时 QQ 音乐不再变小，多次听写监测也未见所记录播放流的增益下降；具体范围见[验证记录](TESTING.md#客户端播放保护实测)。这不能替代每台机器上的连续听写、切歌与语音消息验证，尤其注意旧客户端音频子进程可能尚未退出。应用保护前应结束听写并正常退出客户端，应用后重新打开；不需要为此重启 PipeWire。若当前音量仍异常，先按应用和实际流逐项确认原因，不要将所有程序音量强制设为同一个值。

## 提示客户端播放保护未生效

运行 `/usr/bin/python3 -B scripts/doctor.py` 查看保护检查。安装使用的 `--dictation-helper` 路径必须与 `protect-client --helper` 指向同一个客户端文件。默认路径是 `/usr/lib/chatgpt/resources/native/dictation-ducking`，只接受已核实原程序或本项目替代程序的精确内容。

系统目录需要管理员权限才能写入，原始备份和元数据也以私有权限保存。先由普通用户执行保护预览；实际写入、读取私有备份或恢复时，按[完整说明](../README.md#2-先启用客户端播放保护)使用所需权限。本程序不会自动提升权限，也不会通过改动整个目录权限来绕过检查。

如果客户端更新覆盖了保护，桥接会拒绝继续启动听写；听写中检测到保护失效时会释放 F5。不要绕过此检查或直接恢复旧备份来覆盖新版本，应该先重新核实客户端版本和辅助程序内容，再提供对应适配。

## 能开始和停止录音，但没有波形

先确认 SayAll 日志有音频帧和非零峰值，再确认应用选择的是 `sayall-mic`，且麦克风没有静音。不要只凭按键日志认定已录到声音。

曾实测发现：Codex 的 PipeWire 录音节点 **总增益 `volume=0`**，但声道 `channelVolumes=[1,1]`，PulseAudio 界面仍显示 100%。在实际录音期间，`pw-dump` 中可以查看 `Stream/Input/Audio` 节点的 `Props`。必须结合所属客户端确认目标是 Codex 的录音流，不能仅凭共用的名称 `Chromium input` 判断。

确认是此问题后，可针对确认过的节点 ID 执行 `pw-cli set-param <节点ID> Props '{ volume: 1.0 }'`。节点 ID 会变化，不要复制旧日志里的 ID。本项目不安装持续强制改音量的后台程序。

## 按键没有响应

- 看服务日志是否出现物理遥控器按键。没有则检查精确设备权限和配置地址。
- 运行 `xprop -root _NET_ACTIVE_WINDOW`，用返回的窗口 ID 执行 `xprop -id <窗口ID> WM_CLASS`。应与配置的 `codex_wm_classes` 中某一项准确匹配（不区分大小写）。
- 这种检测只适用于 X11/XWayland 可见的窗口。换到原生 Wayland 窗口时可能不可用；不要用关闭所有焦点检查的方式掩盖问题。
- F5 快捷键必须已经在 Codex 中设置。点一下输入框，长按语音键测试；非常短的点按可能被有意忽略，防止迟到的启动命令留下录音状态。
- 确认键只在 Codex 或已启用的微信窗口中发送 Enter，听写键仍按住时不会发送。返回键在这两类窗口中作为 Backspace，其他软件保留 KEY_BACK；当前软件未处理原始返回键时可以没有明显动作。
- 微信的退格映射需要 `alpha.4` 或更新版本，且微信窗口类名已在 `wechat_wm_classes` 中启用；只更新下载目录不会替换已经安装的运行文件，升级步骤见[微信说明](WECHAT.md#启用微信窗口映射)。

## 蓝牙重连后只有按键，没有麦克风

检查 `sayall-bridge.service` 是否通过本项目包装器启动、是否出现重新订阅 ATVV 的日志。包装器依赖 SayAll 0.3.0 的 Python 接口；更换上游版本后需要重新验证。

BLE 失联时日志中的“遥控器 BLE 连接已断开，需要重建音频订阅”是触发 systemd 重建连接的信号。等待服务重新就绪再测试。如果持续失败，先确认地址、电量和蓝牙连接，而不是反复修改 F5 映射。

## 安装或卸载拒绝覆盖

默认安装命令只是预览，需要 `--apply` 才写文件。实际应用前需要停止 SayAll 和本项目的按键服务。

已有 `ExecStart` 补充配置（drop-in）、返回键映射、未受管理的文件都需要先检查并迁移。卸载发现用户后来改过受管理文件，会保留现场并停止；不要直接删除清单，它包含恢复所需的原内容。
